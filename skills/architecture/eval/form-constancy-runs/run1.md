**Quote generation: synchronous edge path vs. async job pipeline**

**reversibilità:** `OWNED`. All three conditions hold: (a) caller set closed — verified by one grep census pass + import-level check, narrowing 24 textual hits to 3 genuine callers, all inside `backend/app/`; graph-level symbol verification (serena) was not run, so this closure is marked `ASSUMED` below rather than fully closed. (b) every caller sits in the one repo we push — yes. (c) landing the change needs no other party's release, deploy window or approval — yes, per input ("deployed by us, no external consumer of the interface"); the frontend touches only the HTTP `mode="chat"` contract, not these two interfaces directly.

**opzioni:**
- A — Keep the synchronous edge path, add a heartbeat/keep-alive workaround.
- B — Move generation to an async pipeline: job queue + polling or SSE for status.

MECE check: mutually exclusive (generation lifetime is either bound to one HTTP request or decoupled from it — no overlap). Exhaustive: a third variant considered — chunking one large quote into several sub-127s calls — was excluded as a separate branch because it already requires request-external state and multiple round trips, i.e. it is a lower-investment implementation of B's shape, not a third MECE category.

**costo per opzione:**
- A costs: a heartbeat/keep-alive defeats an *idle*-connection timeout (a proxy or client killing an inactive connection); it does not raise the platform's *execution*-duration ceiling. The trigger case named in the input — large quotes already hitting the 127s ceiling — correlates with active compute time, not idleness, which is the signature of a hard wall-clock cap, not an idle one. Modelled against that specific hard scenario (not the easy, already-passing small-quote case), A does not survive it. Even where it does help, it buys no margin against future quote-size growth — the same ceiling gets hit again. It also leaves `chat_runner`'s and the estimator's single blocking call shape unchanged: a failure mid-generation has no partial-progress state and no retry — a full restart.
- B costs: touches both interfaces, plus the API surface — a new job-status/SSE endpoint and a queue+worker subsystem to build, deploy and operate. All 3 existing callers (`chat_stream.py`, `retrieve_tools.py`, `smart_retrieve.py`) and their tests (`test_chat_runner.py`, `test_chat_runner_snapshot.py`, `test_scale_estimator.py`, `test_smart_retrieve.py`) must migrate to the new call shape. It introduces failure modes the sync path never had to answer — duplicate delivery, lost job, worker crash mid-job, client giving up before completion — each needing an explicit answer. The product UX changes from "wait for one response" to "start a job, check on it."

**scelta:** B — the async pipeline. Not because it is cheaper (it plainly is not) but because A's mechanism does not address the scenario the decision exists for: a heartbeat answers idle-timeout risk, and the input names a compute-duration ceiling being hit by size, not idleness. Least-worst: accept B's build/migration/operational cost because A's lower cost buys a fix that does not close the reported failure.

**enforcement:** a CI check (red + comment, non-blocking) over `backend/app/api/` and `backend/app/pipeline/` that flags any route handler or pipeline module invoking `chat_runner.run_chat_v2_stream` or `scale_estimator`'s compute entrypoint directly and synchronously in the request path, instead of through the job-enqueue interface. Outside CI's own gates and the AFK pipeline, per the field's constraint.
